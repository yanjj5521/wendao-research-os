# 任务上传系统：错误提交处理与撤回机制设计

状态：设计稿（v1，2026-11-02）　适用范围：问道科研个人端“资料库/任务上传”
关联模块：`web/routes/library.py`（上传/编辑/删除/任务）、`core/schema/personal.py`
（`entries`/`quests`/`activities`）、`services/economy.py`（修为 XP 与灵石）、
`services/file_storage.py`（附件落盘）、`core/database.py`（settings/迁移）。

---

## 0. 现状与设计原则

**现状**：上传/新建条目即写入 `entries` 并通过 `activities(xp)` 计入修为（`xp_for_kind`）；
任务完成发 XP（`fixed_cultivation_xp`，`quests.xp_awarded` 防重复）；灵石等资产走
`services.economy.transact` 账本。**当前没有人人审核链**，删除条目也不会回收已发奖励。

**原则**：自动化优先（规则可判定的一律系统自动执行），人工干预兜底（涉奖励追回、
疑似恶意、超边界时转管理员）；所有动作写入不可变日志，保证可追溯；失败可回滚
（条目快照 + 附件副本 + 账本冲正三条线都留档）。

## 1. 用户侧撤回申请

### 1.1 入口与所需信息

| 项 | 规则 |
| --- | --- |
| 入口 | ① 条目详情页“更多 → 申请撤回”；② 任务详情页（ quests）“撤回完成”；③ 上传成功后的 toast 内“撤回本次上传”（5 分钟内直达） |
| 必填 | 主体类型（entry/quest）、主体编号、错误类型（枚举，见 1.2）、错误说明（≥10 字） |
| 选填 | 期望处理（仅撤回记录 / 撤回并退附件 / 转为草稿待修改）、附件截图（≤5 张） |
| 自动补全 | 申请时间、当前奖励发放状态（系统查询 activities/transact 自动带入，用户不可改） |

### 1.2 错误类型枚举与自动处置

| 错误类型 | 自动判定 | 默认处置 |
| --- | --- | --- |
| duplicate（重复上传） | 与既有条目标题+内容指纹相似度 ≥0.9 | 自撤回：删条目+附件，冲正 XP |
| wrong_file（传错文件） | — | 自撤回（限时内） |
| wrong_workspace（归档错位） | — | 不撤回，转为“移动到正确工作区”（不冲正，无奖励影响） |
| content_error（内容有误） | — | 限时内自撤回；超时转管理员 |
| privacy（涉密/隐私） | 关键词+用户自述命中 | **立即自动下架**（置 status='hidden'），转管理员复核，奖励冻结 |
| malicious（误标/他人作品等） | 用户自述 | 直接转管理员 |
| other | — | 限时内自撤回，超时转管理员 |

### 1.3 自动化受理机制

受理 = 系统校验（主体存在、属于本人、状态可撤）→ 自动判级（见 §3 边界）→
创建 `upload_withdrawals` 记录（状态 `auto_approved` / `pending_review`）→
按判级立即执行或入管理员队列。**全程不需要用户填写管理员可见字段以外的内容**；
被拒（不可撤）时页面给出具体原因与可选替代动作（如“改为编辑修正”）。

## 2. 奖励处理规则

奖励 = XP（修为，`activities.xp` 汇总）与灵石等资产（`transact` 账本）。

### 2.1 判断规则表

| 维度 | 判定 | 奖励处置 |
| --- | --- | --- |
| 错误性质 | mechanical（重复/传错/内容误） | **全额冲正**：XP 负向 activity + `transact` 负向（如已兑换灵石则记欠账） |
| 错误性质 | privacy | **冻结**（不冲正不发新），管理员裁定后冲正或豁免 |
| 错误性质 | wrong_workspace | **不冲正**（无奖励影响） |
| 是否恶意 | 用户 90 天内 ≥3 次恶意/隐私类撤回，或指纹撞库判定抄袭 | **全额追回 + 90 天内奖励发放冻结**；入审计 |
| 金额阈值 | 单次冲正 XP ≤ 200 或灵石 ≤ 50 | 自动执行 |
| 金额阈值 | 超阈值（如高难任务 XP） | 自动生成冲正单，**管理员一键确认**后执行（防误伤） |
| 账户不足 | 余额 < 应追回 | 差额记入 `reward_adjustments` 欠账（direction=debt），后续奖励入账时按 50% 自动抵扣至清零；不清零不影响功能 |

### 2.2 自动扣减触发条件（全部满足才自动）

1. 撤回申请为 `auto_approved`；
2. 应冲正金额 ≤ 阈值且无恶意标记；
3. 冲正账目可完整对上原始发放记录（activity/transaction id 可回溯）；
4. 执行前自动创建数据库快照（`backup_local_db`）。

任一不满足 → 生成管理员待办（含全部回溯证据），人工处理。

## 3. 用户自撤回边界

| 边界 | 自撤回条件 | 设置依据 |
| --- | --- | --- |
| 时间 | 上传/提交后 **≤ 24 小时**（任务完成后 **≤ 72 小时**） | 覆盖“当晚发现早上传错”场景；超过 24h 通常已被复习/引用，自动删除风险大 |
| 审核状态 | 未进入任何人工审核 | 已被管理员处理说明存在争议，自动改动会破坏裁决一致性 |
| 引用状态 | 未被论文报告/工作台引用（`entry_id` 无外链） | 被引用条目删除会产生断链，须人工评估 |
| 奖励状态 | 已发奖励满足 §2.2 自动冲正条件 | 奖励已被消费/超额时自动冲正会透支账户 |
| 频次 | 同一条目仅可撤回 **1 次**；每日自撤回 ≤ 5 次 | 防刷：反复上传-撤回可刷 XP，频次限制配合恶意标记 |
| 附件 | 文件仍在且可删除 | 附件丢失只撤记录会留下孤儿文件 |

**超出任一边界** → 状态置 `pending_review`，自动转入管理员队列（用户端显示“已提交，
等待管理员处理，预计 48 小时内答复”），用户可补充说明但不能重复提交。

## 4. 管理员侧流程与权限

### 4.1 操作流程

```
待办列表 → 详情（条目快照/奖励账目/用户说明/自动判级依据）
  ├─ 通过撤回：删条目（快照存档）→ 奖励冲正单确认 → 执行 → 通知用户
  ├─ 驳回：填写理由 → 通知用户（可申诉一次）
  ├─ 转迭代修改：驳回撤回 + 建议走 §5 修改流程
  └─ 标记恶意：冻结奖励 + 记入风控
```

### 4.2 权限矩阵

| 能力 | 用户 | 管理员 | 系统 |
| --- | --- | --- | --- |
| 提交撤回申请 | ✅（仅本人主体） | ✅（代处理） | 自动受理 |
| 自撤回执行 | ✅（边界内） | ✅（不限边界） | ✅（自动判级通过时） |
| 奖励冲正 ≤阈值 | 自动 | ✅ | ✅ |
| 奖励冲正 >阈值 | ❌ | ✅（确认制） | 生成待办 |
| 恶意标记/冻结 | ❌ | ✅ | 建议 |
| 查看全量日志 | 仅本人申请 | ✅ | 记录 |

### 4.3 日志与可追溯

- 所有状态流转写 `upload_withdrawals`（含 decided_by/decision_note/时间戳）；
- 奖励冲正写 `reward_adjustments`，并回填原始发放记录 id（activity_id / transaction_id）；
- 条目删除前强制生成 `entry_revisions` 快照（JSON + 附件副本），恢复=从快照重建；
- 个人端写入 `activities`（action=`withdraw_*`），同步入 hub 审计（管理员侧动作）。

## 5. 后续修改机制（迭代修改）

### 5.1 流程

```
条目详情 → “提交修订” → 系统快照当前版本为 rev{n}
  → 用户编辑（内容/文件/元数据），写 rev{n+1}（状态 pending）
  → 自动审：与上一版差异 ≤30% 且无奖励请求 → 直接生效
  → 转人工：差异 >30% / 请求追加奖励 / 涉密词命中 → 管理员审核
```

### 5.2 版本管理与审核规则

| 规则 | 说明 |
| --- | --- |
| 版本号 | `entry_revisions.rev_no` 单调递增；`entries` 主表始终指向当前生效版 |
| 修订说明 | 必填（≥10 字），进入版本时间线，可追溯“为什么改” |
| 生效即替换 | 旧版本保留在快照，可一键回滚（回滚也生成新 rev，不删历史） |
| 新版本奖励 | 修订**默认不发新奖励**；仅当管理员审核通过且修订含实质新增（差异>30% 且审核通过）时，按原奖励的 ≤50% 追加（防“拆分刷分”） |
| 对已发奖励 | 若修订修正了原错误且管理员选择“以修订替代撤回”，则撤销对应撤回单，原奖励保留 |
| 任务(quest)修订 | 完成后补充材料走同流程；`xp_awarded` 已置位则不再重复发 XP |

## 6. 异常情况清单与兜底

| 异常 | 兜底策略 |
| --- | --- |
| 重复撤回（同主体多单） | 唯一约束 `(subject_type, subject_id, status in active)`；二次提交提示“已有处理中的撤回单” |
| 撤回与审核并发 | 所有状态变更走 `BEGIN IMMEDIATE` + 状态机校验（仅 pending_review→decided 可跃迁）；冲突方收到“该条目状态已变化” |
| 撤回时条目已被删除 | 申请单自动关闭为 `obsolete`，通知用户 |
| 奖励不足无法追回 | 差额转欠账（§2.1），后续奖励自动抵扣；永不扣成负余额 |
| 冲正执行中断（崩溃） | 先写 `reward_adjustments(status=pending)` 再执行，重启后幂等重放 |
| 附件文件丢失 | 仅撤记录；日志标记 `file_missing`；不阻塞流程 |
| 管理员超时未处理（>48h） | 系统提醒 + 自动升级：低风险单按自动判级结论执行 |
| 用户对驳回申诉 | 每单可申诉一次，二次转“管理员复核”队列并置顶 |
| 修订与撤回并发 | 同一主体同一时刻只允许一个活动单（撤回或修订），先到先得 |
| 数据集被下游分析引用 | 删除改为“下架”（status='hidden'），分析页提示来源已下架 |
| 批量撤回请求 | 单次 ≤10 条，超出转管理员批量工具 |
| 时间边界按谁算 | 统一按服务端 `created_at`（本地时区 ISO），不接受客户端时间 |

## 7. 数据模型与实施锚点

**新增表**（迁移沿用幂等 `PRAGMA table_info` 检查模式）：

- `upload_withdrawals(id, subject_type, subject_id, requester_id, error_type, description,
  status, auto_level, decided_by, decision_note, created_at, decided_at)`
- `entry_revisions(id, entry_id, rev_no, snapshot_json, file_copy_path, note, status,
  created_by, created_at, reviewed_by)`
- `reward_adjustments(id, subject_type, subject_id, kind(xp/spirit_stone), amount,
  direction(reversal/debt/grant), reason, withdrawal_id, origin_activity_id,
  origin_transaction_id, status, created_by, created_at)`

**路由锚点**（`web/routes/library.py`）：

- `POST /entry/{id}/withdraw`、`POST /quest/{id}/withdraw`
- `POST /entry/{id}/revise`、`POST /revision/{id}/activate`
- 管理侧（如引入团队审核）：挂 `hub/routes/admin.py`，全部动作 `audit()`

**发放侧埋点**：`upload_post`/`entry_create`/`quest complete` 发奖励时记录
`origin_activity_id`，供冲正回溯（当前缺这层映射，是实施 M2 的前置）。

**分期**：M1 自撤回+快照+日志（无奖励影响）→ M2 奖励冲正/欠账 → M3 迭代修订与版本管理。
