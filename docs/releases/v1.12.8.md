# 问道科研 1.12.8

发布日期：2026-11-06

本版是一次**多用户并发稳定性 + 运行速度**专项：先量化定位问题，再逐项修复，最后用新增的并发回归测试证明行为一致。

## 一、重构前发现的问题点（全部有复现）

| # | 问题 | 证据 | 影响 |
| --- | --- | --- | --- |
| P1 | **福利额度可被并发超发**：发放的"读额度→入账"在 deferred 事务里执行，两个管理员同时发放都能读到同一份"本周已用"，各自通过检查后插入 | SQLite deferred 事务读-写竞态；用双管理员并发发放复现 | 福利超出每周上限 |
| P2 | **额度生成自死锁**：`weekly_quotas` 在调用方已持有写锁时，另开连接再 `BEGIN IMMEDIATE`，等自己的锁直到 busy_timeout 报 `database is locked` | 新增并发测试第一轮即复现（10 秒超时） | 首次发放福利可能失败 |
| P3 | **每请求设置读取开销**：`get_setting` 每次调用都新开 SQLite 连接并执行 4 条 PRAGMA；单个页面请求会读十余次设置 | 166 处调用；`context()` 每页 4–8 个连接 | 多用户时连接风暴、延迟叠加 |
| P4 | **总修为每页全表 SUM**：`total_xp` 对持续增长的 `activities` 做全表聚合，每个页面渲染一次 | `context()` 每请求调用 | 数据越积累越慢 |
| P5 | **中心资产统计缺精准索引**：余额/额度统计按 `(user_id, asset_key)` 过滤，但只有 `(user_id, created_at)` 索引 | EXPLAIN 查询形态 | 成员越多扫描越多 |
| P6 | **中心未捕获异常无友好页**：只有 HTTPException 处理器，未捕获异常直接裸 500 | `hub/app.py` 仅有 1 个 handler | 一个成员的报错吓到所有人 |
| P7 | **页面读连接被升级为写事务**：管理台读连接在额度首次生成时执行 INSERT，与其它写者互等直到 `database is locked` | 并发测试与锁探测复现；登记表追踪到 `in_transaction=True` 的页面连接 | 管理台/发放偶发 500 |
| P8 | **市场资金操作仍是 deferred 事务**：交换接受、红包发送等"检查→转账"存在同类竞态 | 与 P1 同类 | 灵石/材料双花或超付 |

## 二、修复方案与实现

| # | 方案 | 实现 |
| --- | --- | --- |
| F1 (P1) | 发放改为**写事务**：`hub_transaction(immediate=True)`，"检查额度+插入+审计"对外部并发原子 | `hub/routes/admin.py` |
| F2 (P2) | `weekly_quotas` **复用调用方事务**：调用方已传 `conn` 时不再另开连接；只有独立调用才自己开 immediate 事务。并发首写以 `INSERT OR IGNORE` 后的库内值为准 | `hub/db.py` |
| F3 (P3) | `get_setting` 进程内缓存：**1 秒 TTL** + `set_setting` 写穿透 + `clear_settings_cache()` 供测试/迁移使用 | `core/database.py` |
| F4 (P4) | `total_xp` 以 `MAX(id)` 为失效守卫：activities 无新记录时直接复用上次 SUM（记录只增不删，守卫完备） | `core/database.py` |
| F5 (P5) | 中心库 **v6 → v7**：`idx_hub_assets_user_asset(user_id, asset_key)`，建表语句与迁移同步 | `core/schema/hub.py`、`core/migrations.py` |
| F6 (P6) | 中心端补 `Exception` 级处理器：API 返回 JSON，页面渲染友好错误页 | `hub/app.py` |
| F7 (P7) | **写路径与读连接严格分离**：额度生成只在「调用方已开写事务」时复用其连接，否则走独立 immediate 事务，读连接永不升级 | `hub/db.py::weekly_quotas` |
| F8 (P8) | 市场资金操作（红包发送、交换创建/接受/取消）全部改为 immediate 写事务 | `hub/routes/market.py` |

## 四、已知边界（如实说明）

- 设置缓存 TTL 1 秒：直接用 SQL 改 `settings` 表的值，最多延迟 1 秒才被读到（程序内所有写路径都走 `set_setting`，不受影响）。
- `total_xp` 守卫依赖"activities 只增不删"这一现状；未来若做活动清理功能，需要同步失效缓存（函数注释已写明）。
- 镜像下载通道仍依赖第三方可用性；失败会回退直连/续传（1.12.5–1.12.6 已有机制，本版未改动）。
