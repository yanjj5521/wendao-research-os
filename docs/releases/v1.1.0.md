## 新增：迁移执行器（`core/migrations.py`）

三条硬承诺，全部有契约测试：

1. **版本化**：迁移是带版本号的对象（`Migration`），按序执行，结果记入 `schema_migrations`。库经历了什么，事后可查。
2. **快照先行**：任何迁移执行前，用 SQLite backup API 把整个库复制到 `instance/migration_snapshots/`（backup API 保证 WAL 下的一致性；保留最近 5 份）。失败也有快照可回。
3. **失败回滚**：迁移整体原子。任何一条语句失败，结构变更、版本号、迁移记录一起回滚，程序报出明确错误并指向快照位置。

### 实现里值得记录的一个坑

SQLite 的 Python 驱动只在 DML 前隐式开事务，**DDL（ALTER/CREATE）会立即提交**。第一版迁移器因此"看起来回滚了、其实列已经加上"。修正方式是迁移器自己管理事务边界：`BEGIN IMMEDIATE` → 执行 → `COMMIT`，异常时 `ROLLBACK` 并显式复位 `user_version`。契约测试专门用"先 ALTER 再写坏 SQL"验证了这一点。

## 使用方式

```python
from core.migrations import Migration

PERSONAL_MIGRATIONS.append(
    Migration(
        version=3,
        note="为条目增加 lang 字段",
        statements=(
            "ALTER TABLE entries ADD COLUMN lang TEXT NOT NULL DEFAULT '';",
            "UPDATE entries SET lang='zh' WHERE lang='';",
        ),
    )
)
```

然后把 `core/schema/personal.py` 的 `SCHEMA_VERSION` 加 1。下次启动时自动执行，无需手动操作。中心端同理（`HUB_MIGRATIONS` + `HUB_SCHEMA_VERSION`）。

规则：**已发布的 Migration 不可修改**——写错了就追加一个新版本去修正，保证每台设备上的迁移序列一致。

## 其他

- `init_db` 增加"外来数据库"守卫：`instance/` 下出现没有 `schema_migrations` 的库文件（例如别的工具的 SQLite），会明确拒绝而不是报一个看不懂的错误。
- 中心库同规则。3.x 中心库与本版账号模型不兼容，会被明确指出。
- 数据库"比程序新"（版本号更高）时拒绝打开，防止旧程序把新结构改坏。

## 验证

## 已知边界

- 迁移是**顺序执行**的，不支持多机并发迁移（单用户/小团队场景不构成问题）。
- 快照只保留 5 份；如需更久，手动备份 `instance/migration_snapshots/`。
